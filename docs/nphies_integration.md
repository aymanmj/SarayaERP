# توثيق تكامل نظام السرايا الطبي مع منصة نفيس (NPHIES Integration)

يوفر هذا المستند تفاصيل تقنية حول كيفية ربط وتكامل **نظام السرايا الطبي (Saraya Medical ERP)** مع المنصة الوطنية الموحدة للمعلومات الصحية في المملكة العربية السعودية (**NPHIES**)، اعتماداً على معايير **FHIR R4** وبروتوكولات التشفير والتوقيع الإلكتروني المعتمدة.

---

## 1. البنية الهندسية للتكامل (Integration Architecture)

يعتمد نظام التكامل على معمارية الخدمات المصغرة والربط المباشر بطلب استجابة (Request-Response) عبر نقاط نهاية آمنة لـ NPHIES، مع دعم تشغيل غير متصل بالإنترنت وقائمة انتظار مرنة لإعادة المحاولة (Outbound Queue).

### المكونات البرمجية الرئيسية:
1. **`NphiesService`**: المسؤول عن بناء موارد FHIR الأساسية (Patient, Coverage, MessageHeader, Bundle).
2. **`NphiesCryptoService`**: المسؤول عن معالجة التواقيع الرقمية والتشفير وتطبيق التوقيع الإلكتروني JWS.
3. **`NphiesAuthService`**: المسؤول عن معالجة المصادقة الثنائية (mTLS) وتبادل رمز الوصول (OAuth 2.0).
4. **`NphiesClaimService`**: المحرك الرئيسي لإرسال المطالبات والموافقات المسبقة والاستعلام عن حالتها.
5. **`ConnectivityService` & `OutboundQueueService`**: معالجة حالات انقطاع الاتصال وجدولة الإرسال التلقائي الخلفي.

## 2. بروتوكول التوقيع الرقمي (JWS Signatures)

تشترط منصة NPHIES توقيع جميع حزم (Bundles) ومروّسات الرسائل (MessageHeader) رقمياً باستخدام معيار **JWS (JSON Web Signature)** لضمان موثوقية المرسل وعدم التلاعب بالبيانات.

### آلية عمل `NphiesCryptoService`:
- **خوارزمية التوقيع**: يعتمد النظام على خوارزمية **RS256** (أو **ES256**) لتوليد التوقيع الرقمي المفصول (Detached JWS).
- **إدارة المفاتيح الآمنة**:
  - يتم تحميل المفتاح الخاص (`NPHIES_PRIVATE_KEY`) من متغيرات البيئة الآمنة للإنتاج (عبر HashiCorp Vault أو إعدادات النظام المحمية).
  - يمكن تحديد مسار الملف عبر متغير البيئة `NPHIES_PRIVATE_KEY_PATH`.
  - يدعم النظام "الوضع الوهمي" (Dummy Mode) لبيئات التطوير والاختبار المحلي لمنع توقف عمل المطورين في حال عدم توفر المفاتيح الرسمية.

### كود توليد التوقيع (JWS Signature Generation):
```typescript
const header = { alg: 'RS256', typ: 'JWT' };
const encodedHeader = base64urlEncode(JSON.stringify(header));
const encodedPayload = base64urlEncode(JSON.stringify(payload));
const signInput = `${encodedHeader}.${encodedPayload}`;

const signer = crypto.createSign('RSA-SHA256');
signer.update(signInput);
signer.end();

const signature = signer.sign(privateKey);
const encodedSignature = base64urlEncode(signature);

const detachedSignature = `${encodedHeader}.${encodedPayload}.${encodedSignature}`;
```

## 3. مطابقة الموارد وتنسيق البيانات (FHIR R4 Resource Mappings)

يقوم نظام السرايا بتحويل الكيانات الداخلية لقاعدة البيانات (Prisma Models) إلى موارد متوافقة مع مواصفة **FHIR R4** السعودية الخاصة بـ NPHIES:

### أ. مورد المريض (Patient Resource)
يتم إنشاؤه بواسطة `nphiesService.buildPatient` ويربط الحقول التالية:
- الاسم الكامل للمريض (`fullName`)
- الهوية الوطنية أو الإقامة (`nationalId`)
- تاريخ الميلاد (`dateOfBirth`)
- الجنس (`gender`)
- رقم الجوال (`phone`)

### ب. مورد التغطية التأمينية (Coverage Resource)
يربط علاقة المريض بشركة التأمين الحاضنة:
- معرّف العضوية (`memberId`)
- معرّف جهة الدفع (`payerIdentifier` - رمز شركة التأمين المعتمد لدى مجلس الضمان الصحي)
- اسم جهة الدفع (`payerName`)
- مرجع المريض (`Patient/{patientId}`)

### ج. مورد مقدم الخدمة (Organization Resource)
يمثل المستشفى أو المركز الطبي المرسل للمطالبة:
- نظام الترخيص: `http://nphies.sa/license/provider-license`
- القيمة: رمز المنشأة المعتمد في السرايا (`hospital.code`)

### د. مورد المطالبة (Claim Resource)
يحتوي على كافة البنود السريرية والمالية:
- **التشخيصات (Diagnosis)**: يتم تحويل رموز التشخيص من الملف الطبي للمريض إلى تصنيف **ICD-10** العالمي والمحلي.
- **الخدمات والإجراءات (Items)**: يتم مطابقتها مع أكواد الإجراءات المعتمدة لدى NPHIES (`http://nphies.sa/terminology/CodeSystem/procedures`).
- **التسعير**: تحديد الأسعار لكل خدمة بالريال السعودي (`SAR`) وحساب إجمالي المطالبة بدقة.

### هـ. مورد الترويسة والحزمة (MessageHeader & Bundle)
- يتم استخدام `MessageHeader` لتحديد نوع المعاملة (مثل `claim-request` أو `preauthorization-request`).
- يتم دمج كافة الموارد السابقة في حزمة موحدة من نوع `message` لإرسالها دفعة واحدة.

## 4. نظام التعامل مع انقطاع الاتصال (Offline & Queue Management)

لضمان عدم ضياع أي مطالبات مالية عند حدوث مشاكل في شبكة الإنترنت أو توقف خوادم NPHIES:

1. **التحقق من الاتصال**: يستخدم النظام `ConnectivityService.isOnline()` للتحقق من حالة الاتصال الفعلي بالمنصة.
2. **قائمة الانتظار (Queue)**: إذا كان النظام غير متصل:
   - يتم إدراج المطالبة في قائمة الانتظار الخلفية (`OutboundQueueService`).
   - يتم تحويل حالة المطالبة في قاعدة البيانات إلى `QUEUED`.
   - يتم تسجيل العملية في سجل المطالبة (`ClaimHistory`).
3. **المزامنة الخلفية**: تقوم مهمة خلفية مجدولة (Cron Job) بمحاولة إعادة إرسال المطالبات الموجودة في قائمة الانتظار فور استعادة الاتصال بالشبكة.

## 5. إدارة ومعالجة الأخطاء وترجمتها (Error Handling)

تستخدم منصة NPHIES رمز الاستجابة `OperationOutcome` للإبلاغ عن أخطاء التحقق من البيانات. يقوم نظام السرايا بترجمة هذه الرموز تقنياً وسريرياً لتبسيط المعالجة لموظفي الحسابات الطبية:

| الرمز الفني (FHIR Code) | رسالة الخطأ المعربة | التوصيف السريري/التقني |
| :--- | :--- | :--- |
| `security` | مشكلة أمنية أو عدم صلاحية الشهادات (mTLS/JWS). | فشل في التحقق من شهادة الاتصال أو التوقيع الرقمي للمسودة. |
| `invalid` | البيانات المرسلة غير صحيحة أو غير مكتملة. | وجود نقص في البيانات الإجبارية كالهوية أو أكواد التشخيص. |
| `not-found` | لم يتم العثور على المريض أو البوليصة في سجلات التأمين. | عدم تطابق بيانات المريض أو رقم العضوية مع خوادم شركة التأمين. |
| `expired` | بوليصة التأمين منتهية الصلاحية. | محاولة إرسال مطالبة لتاريخ خارج نطاق صلاحية البوليصة. |
| `business-rule` | تم رفض الطلب بناءً على قواعد التأمين (Business Rule). | مخالفة أحد الشروط المالية أو السريرية لعقد التأمين. |
| `timeout` | انتهى وقت الاتصال بمنصة نفيس. | تعذر الحصول على رد من منصة NPHIES في الوقت المحدد. |
