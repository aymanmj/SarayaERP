# تحديث تفويض الموظفين وسحب الصلاحيات — 2026-11-07

مرجع الحالة: [السجل الموحد](REMEDIATION_REGISTER_2026-11-07_AR.md)،البند JWT02،مع ارتباط جزئي بـOPS01 وJWT01. الحالة:منفذ ومختبر ضمن نطاق HTTP للموظفين؛لا تشمل المرحلة إبطال اتصالات WebSocket القائمة أو اكتمال دورة الجلسات كلها.

## المشكلة والسلوك الناتج

كان تحقق JWT يعيد claims الرمز بعد فحص نشاط الحساب وتصريح المنشأة. لهذا قد يستمر ADMIN أو ADMIN_FULL_ACCESS أو isSuperAdmin أو إذن مسحوب في الوصول حتى انتهاء الرمز؛بعض المتحكمات تقرأ هذه القيم مباشرة خارج PermissionsGuard.

أصبح الرمز الموقع يثبت هوية الموظف والفرع المختار. يعيد JwtStrategy تحميل الأدوار وصلاحياتها من قاعدة البيانات في كل طلب،ويشتق isSuperAdmin من دور SUPER_ADMIN الحالي،ويأخذ organizationId من الفرع المصرح الحالي. ينشئ هوية جديدة محددة الحقول للطلب وCLS دون نسخ امتيازات الرمز أو patientId. يبقى تحقق التوقيع والمصدر saraya-staff والانتهاء ونشاط الحساب والمنشأة وتصريح الفرع. فشل قراءة قاعدة البيانات يمنع الطلب دون الرجوع إلى امتيازات سابقة محفوظة.

سحب دور أو إذن أو تصريح فرع بعد اعتماد التغيير في قاعدة البيانات يسري على طلب HTTP التالي،حتى عند إعادة استخدام JWT السابق. لا يلزم تسجيل خروج لإيقاف ذلك الإذن. إضافة إذن حالي تسري أيضًا دون إعادة إصدار الرمز؛الاختبارات تتحقق من المنع والوصول الصحيح معًا.

أضيف GET /auth/me محميًا بتحقق الموظفين،مع Cache-Control:no-store،لإرجاع هوية التفويض الحالية فقط. لا يعيد كلمة المرور أو رموز التحديث أو ملف المستخدم الكامل. لم يُربط بعد بتحديث دوري لصلاحيات واجهة المستخدم؛قد يبقى زر قديم ظاهرًا بينما يرفض الخادم تنفيذه.

## سلامة تعديل الأدوار العامة

بقي تعديل صلاحيات الدور العام مقيدًا بإدارة المنصة وبصلاحية users:manage. أضيف DTO يمنع القيم غير الصحيحة والمكررة،وفحص الخدمة يمنع تجاوز التحقق عند الاستدعاء الداخلي. القائمة الفارغة مسموحة عمدًا لسحب جميع أذونات الدور.

تجري عملية الاستبدال داخل معاملة واحدة،مع قفل صف Role،وفحص وجود الدور وجميع الصلاحيات قبل حذف العضويات السابقة. فشل إدراج البديل يعيد القائمة السابقة كاملة. تتسلسل عمليتا تعديل الدور نفسه؛النتيجة إحدى القائمتين المكتملتين،دون دمجهما أو ترك حذف جزئي. هذا لا يضيف إقرارًا ثانيًا أو إدارة نسخ/موافقة للأدوار،ولا يغلق عموم OPS01 أو OPS03.

## حدود الإغلاق والمتابعة

1. لا تلغي المرحلة طلبًا بدأ تفويضه قبل اعتماد السحب؛العمليات الحساسة قد تحتاج إعادة فحص داخل معاملة العمل بحسب سياسة محددة.
2. لا توجد هنا قائمة إبطال jti أو إصدار جلسة يبطل كل رموز الوصول عند الخروج/تغيير كلمة المرور. إعادة تنشيط الحساب قد تجعل رمزًا لم ينته صالحًا ضمن الأذونات الحالية؛هذه متابعة مستقلة لدورة الجلسة.
3. أحداث WebSocket لا تمر تلقائيًا بهذه الاستراتيجية؛بقي SEC04 جزئيًا،وبخاصة إبطال اتصال قائم وإعادة فحص أدوار غرفه. لم نعتبر HTTP دليلًا على إصلاحها.
4. الأدوار الحالية عامة للمستخدم بين فروعه المصرحة؛لا تخصيص جديد للأدوار بحسب الفرع،ولا إثبات شامل لكل علاقة/مسار في SEC03 وOPS02.
5. لا cache للصلاحيات في هذا التغيير. تبقى قياسات الحمل وP95 وعدد الاستعلامات وتقييم الفهارس مطلوبة؛لم يُدّع تحسن الأداء.
6. اختبارات النجاح والرفض والتراجع ليست قبولًا بشريًا أو تدقيق اختراق مستقلًا،ولا تثبت اكتمال بقية بنود السجل.
